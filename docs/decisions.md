## D-006 合并为单一项目（取代 D-001）

- **日期**：2026-11-02
- **状态**：✅ 已确认，取代 D-001
- **决策**：博客与文件系统在**同一项目、同一仓库、同一台服务器**上，以**模块**形式区分。
- **用户理由**：个人数据量小；两个服务配置成本高、浪费资源；模块化可一起部署。
- **代价（必须知晓）**：
  - **容错率变低，不是变高。** 合并后任一模块故障会导致整站不可用；只有分开部署才能隔离故障。个人站点可接受，但不得误认为合并提升了容错。
  - 服务器成本与运维责任由自己承担。
- **结论**：个人规模下合并合理，但必须明确以上代价。

## D-007 混合渲染架构

- **日期**：2026-11-02
- **状态**：✅ 已确认
- **决策**：
  - 访客端页面 → 静态生成，追求速度与 SEO
  - 管理后台、文件系统 → 服务端动态处理
  - 二者在同一 Astro 项目中并存，按路由区分
- **理由**：同时获得静态页面的性能与动态功能的能力，避免全站 SSR 的性能损失。
- **备注**：这是 D-003「Astro 是否够用」疑虑的解法。

## D-008 部署方式：自建服务器

- **日期**：2026-11-02
- **状态**：✅ 已确认
- **决策**：不使用 Vercel / Cloudflare 等平台，自建 Linux 服务器（ECS 或轻量应用服务器）。
- **理由**：上述平台在中国大陆访问不稳定（域名解析污染、速度波动），不适合面向大陆访客的站点。
- **待确认**：服务器是否已购买、地域选择（影响 ICP 备案），见 Q-09。
- **阶段说明**：

  - 加入动态功能后：需常驻 Node 进程 + 数据库 + Nginx 反向代理

## D-009 内容存储：数据库驱动

- **日期**：2026-11-02
- **状态**：✅ 已确认
- **决策**：文章等内容存入**数据库**，不采用 Git 驱动的 Markdown 方案。
- **理由**：用户后台规模庞大，需要统计、批量操作、复杂筛选等能力，Git 驱动方案无法支撑；数据库方案可实时生效。
- **代价**：必须自行做**定时备份**——代码在 GitHub 有副本，数据库里的文章只有一份。

## D-010 渲染策略：按需生成 + 缓存

- **日期**：2026-11-02
- **状态**：🟡 推荐方案，待用户最终确认（Q-12）
- **问题**：静态页面不会自动更新。后台改完数据后，已生成的 HTML 仍是旧的，用户刷新只会拿到同一个旧文件。
- **决策**：访客页面**首次访问时现场生成**，结果存入缓存；后续访问直接返回缓存。后台保存数据时**主动清除对应缓存**，使下一个访客看到新内容。
- **被否备选**：发布后触发全站重新构建。缺点是改一次要等几十秒到几分钟，对功能庞大的后台体验差。
- **效果**：访客速度接近真静态，后台修改即时生效。

## D-011 文件存储架构：元数据与内容分离

- **日期**：2026-11-02
- **状态**：✅ 已确认
- **决策**：
  - 文件**元数据**（URL、大小、类型、状态、引用关系）→ 数据库
  - 文件**内容**（图片、视频、附件）→ 对象存储（阿里云 OSS）
  - 文章正文中的图片以 **URL 形式**内嵌，数据库不存二进制
- **判断标准**：内容是否为独立二进制文件。是 → 存 OSS；否（文字、Markdown 表格）→ 存数据库。
- **选择 OSS 的理由**：同地域内网访问不计公网流量；容量弹性扩展，比扩容服务器磁盘便宜。
- **必须处理的副作用**：孤儿文件与引用关系，见 D-012。

## D-012 术语约定与文件清理策略

- **日期**：2026-11-02
- **状态**：✅ 已确认
- **命名约定**：用户暂定将网页版资源管理器称为「**文件系统**」。
- **层级约定**：模块（系统切分）→ 功能（用户能力）→ 页面（界面载体）。需求文档中 F/B/S 编号对应模块，每条为功能。
- **清理原则**：**宁可漏删，不可错删。** 存储成本低，误删文件不可恢复。
- **三层机制**：
  1. 上传即登记 `files` 记录，状态为「临时」
  2. 文章保存时解析正文 URL，将引用到的文件标记为「已使用」
  3. 定时任务将长期未引用的临时文件移入回收站，不直接物理删除
- **引用关系表** `file_references`：记录 file_id 与 article_id，支持双向查询——既查「这张图被哪些文章用了」，也查「这篇文章用了哪些图」。
- **删除拦截**：删除文件前，后端查询引用关系并返回关联文章列表；前端弹出提示，标题可点击跳转。被引用的文件默认不可删除（待 Q-10 最终确认）。
- **简化选项（个人规模适用）**：文件只增不减 + 后台提供「未被引用的文件」列表由用户手动清理，实现更简单且不会误删。

## 附一：三种渲染方式

| 方式 | HTML 生成时机 | 特点 |
|---|---|---|
| 静态生成 SSG | 构建时一次性生成 | 快、便宜、可 CDN；内容变动需重新生成 |
| 服务端渲染 SSR | 每次请求现场拼装 | 内容实时；需服务器常驻 |
| 客户端渲染 CSR | 在浏览器内用 JS 渲染 | 首屏慢；适合复杂交互 |

## 附二：三个框架对比

| 框架 | 定位 | 优点 | 缺点 |
|---|---|---|---|
| Next.js (React) | 全栈全能 | 一体化；生态最强 | 概念多，需清楚每段代码运行位置 |
| Astro | 内容优先 | 静态输出性能最佳、学习曲线平缓；支持混合渲染 | 动态功能需自行接入服务端 |
| Nuxt 3 (Vue) | 全栈，对标 Next.js | 能力与 Next.js 相当 | 中文生态资料相对少 |

## 附三：文件存储方案对比

| 方案 | 本质 | 关键差别 |
|---|---|---|
| 阿里云 OSS（本项目选定） | 对象存储 | 同地域内网免流量费，国内访问稳定 |
| Cloudflare R2 | 对象存储 | 下载不收流量费，但国内访问不稳 |
| AWS S3 | 对象存储（行业标准） | 工具链最全，出站流量较贵 |
| Supabase Storage | 存储 + 数据库 + 登录打包 | 开箱即用，但同样存在国内访问问题 |
| 自建 MinIO | 自托管对象存储 | 运维自理；是从云存储过渡到 NAS 的跳板 |

## 附四：对象存储与数据库的分工

- **对象存储**：扁平结构，只有「key → 内容」映射，没有真实目录；界面上的文件夹是模拟的。
- **数据库**：存结构化元数据，支持按条件查询、排序、关联。
- **网页版网盘** = 数据库存目录树 + 对象存储存内容，二者配合。
- **图书馆比喻**：数据库是目录卡片柜（知道书在哪），存储是书架本身（放着书）。
