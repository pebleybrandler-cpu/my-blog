## D-006 合并为单一项目（取代 D-001）

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：博客与文件系统在**同一项目、同一仓库、同一台服务器**上，以模块区分。
- **用户理由**：个人数据量小；两个服务配置成本高、浪费资源；模块化可一起部署。
- **代价（必须知晓）**：**容错率变低，不是变高**。合并后任一模块故障会导致整站不可用；只有分开部署才能隔离故障。个人站点可接受，但不得误认为合并提升了容错。

## D-008 部署方式：自建服务器

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：不使用 Vercel / Cloudflare 等平台，自建 Linux 服务器（ECS 或轻量应用服务器）。
- **理由**：上述平台在中国大陆访问不稳定（域名解析污染、速度波动）。
- **进度**：**服务器尚未购买**。用户决定先本地开发跑通，再部署上线。
- **风险提醒**：若最终使用国内服务器，**ICP 备案需 7～20 个工作日**，应在代码接近完成时即启动备案，避免干等。

## D-009 内容存储：数据库驱动

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：文章等内容存入数据库，不采用 Git 驱动的 Markdown 方案。
- **理由**：后台规模庞大，需要统计、批量操作、复杂筛选；数据库方案可实时生效。
- **代价**：必须自行做**定时备份**——代码在 GitHub 有副本，数据库里的文章只有一份。

## D-010 渲染策略：按需生成 + 缓存

- **日期**：2026-11-02｜**状态**：✅ **已确认**（用户于 2026-11-02 拍板）
- **问题**：静态页面不会自动更新。后台改完数据后，已生成的 HTML 仍是旧的，用户刷新只会拿到同一个旧文件。
- **决策**：访客页面按需生成并缓存；后台保存时主动使对应缓存失效，使下一个访客看到新内容。
- **实现**：随 D-013 改用 Next.js 后，由 **ISR（增量静态再生）** 原生支持——`revalidate` 定时刷新，或后台保存时调用 `revalidatePath()` 精确失效。
- **效果**：访客速度接近真静态，后台修改即时生效。
- **被否备选**：发布后触发全站重新构建（改一次要等几十秒到几分钟）。

## D-011 文件存储架构：元数据与内容分离

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：文件元数据存数据库；文件内容存对象存储（阿里云 OSS）；文章正文中的图片以 URL 内嵌，数据库不存二进制。
- **判断标准**：是否为独立二进制文件。是（图片/视频/附件）→ OSS；否（文字、Markdown 表格）→ 数据库。
- **选择 OSS 的理由**：同地域内网访问不计公网流量；容量弹性扩展，比扩容服务器磁盘便宜。

## D-012 术语约定与文件清理策略

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **命名约定**：网页版资源管理器称「**文件系统**」（亦称资源库，见 D-016）。
- **层级约定**：模块（系统切分）→ 功能（用户能力）→ 页面（界面载体）。F/B/S/U 编号对应模块。
- **清理原则**：**宁可漏删，不可错删。**
- **三层机制**：上传登记为「临时」→ 文章保存时标记「已使用」→ 定时将长期未引用的临时文件移入回收站。
- **引用关系表** `file_references`：记录 file_id 与 article_id，支持双向查询。
- **删除拦截**：删除前查询引用关系并返回关联文章列表，前端提示；是否允许强删由配置决定（见 D-018 / B-07）。

## D-013 技术栈变更为 Next.js（取代 D-003）

- **日期**：2026-11-02｜**状态**：✅ 已确认，取代 D-003
- **决策**：使用 **Next.js（App Router）** 替代 Astro。
- **用户动因**：参考他人博客项目，认为 Next.js 更合适；并意识到后台规模庞大。
- **技术理由**：
  - Astro 的岛屿架构适合「内容为主、少量交互」，而本项目后台与文件系统几乎全是交互。
  - Next.js 单项目内可同时做静态生成页与动态页面，**两侧都不将就**。
  - 后台 UI 生态最成熟（表格、表单、编辑器、图表均有现成组件）。
  - **D-010 的缓存策略由 ISR 原生支持**，比 Astro 自行配置 Nginx 缓存更简单。
- **代价**：概念较多（App Router、Server Component、Client Component），学习曲线陡于 Astro。

## D-014 中英双语内容模型

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：支持中文与英文双语，采用「主表 + 翻译表」结构：
  - `posts`：文章主体（分类、创建时间等共享信息只存一次）
  - `post_translations`：各语言版本（locale、title、content、slug）
- **URL 规则**：带语言前缀，如 `/zh/blog/...`、`/en/blog/...`
- **SEO**：输出 `hreflang` 标签，告知搜索引擎两个版本属同一内容。
- **未翻译处理**：允许某篇文章只有中文版；英文读者访问时的提示方式待定（Q-19）。
- **成本提醒**：双语意味着每篇文章要写两遍，建议只对重要文章提供英文版，不强求全量翻译。

## D-015 用户体系与认证

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **登录方式**：
  - **GitHub OAuth**：免审核，登录即通过（信任第三方平台认证）
  - **邮箱 + 密码**：自行注册，但**必须经站主审核**后才能登录
- **不做邮箱验证**：人工审核已覆盖真实性校验，因此不需要发送验证邮件。
- **忘记密码**：由站主在后台手动重置，不依赖邮件服务。
- **收益**：**整个系统无需配置任何邮件服务（SMTP）**，规避国内服务器 25 端口封禁与邮件进垃圾箱的问题。
- **权限**：访客登录后仅具备浏览与下载权限，无写入权限（见 D-016）。
- **未定**：GitHub 登录是否需要白名单限制（Q-17）。

## D-016 文件系统定位：资源库，非个人网盘

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **决策**：文件系统模块定位为「**资源库**」，存放文章配图与对访客开放的资源文件。
- **关键前提**：用户明确表示**不会上传私人文件**，因此**不实现权限隔离**。
- **权限模型**：
  - 访客（已登录）：浏览、查看、下载
  - 访客：**不可上传**
  - 站主：上传、重命名、移动、删除
- **备选建议（未采纳）**：保留一个 `visibility` 字段作未来退路——成本为零，将来若需存放私密文件无需改表结构。用户未明确表态（Q-16）。
- **概念提醒**：即便不做隔离，也应意识到「资源分享区」与「个人存储」是两种语义；若将来混合使用，需重新评估权限设计。

## D-017 设计强度分档

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **原则**：**该好看的地方做到极致，该干活的地方干净利落。**
- **分档**：
  - 访客端博客：特别漂亮，是网站门面
  - 管理后台：同样讲究设计，站主每天面对
  - 文件系统等工具页：极简，功能优先，不加装饰

## D-018 首次运行向导与设置中心

- **日期**：2026-11-02｜**状态**：✅ 已确认
- **背景**：文件删除策略（禁止 / 警告后放行）不应写死，应交给使用者配置。
- **决策**：
  1. 提供一个**首次运行向导**，在系统未初始化时强制引导配置
  2. 同时提供常驻的**设置中心**，所有策略项可随时修改
- **向导步骤**：环境自检 → 数据库连接 → 创建管理员 → 站点信息 → 策略选择 → 完成
- **设计原则**：向导只放「不填就无法运行」的项，能后配的一律放设置中心；向导越长越容易被跳过。
- **安全要求（重要）**：**初始化完成后必须彻底关闭 `/setup`**，检测到已安装则返回 404。否则任何人都能重新初始化、夺取管理员权限。需重装时必须手动修改服务器文件或环境变量。

## 附一：三种渲染方式

| 方式 | HTML 生成时机 | 特点 |
|---|---|---|
| 静态生成 SSG | 构建时一次性生成 | 快、便宜、可 CDN；内容变动需重新生成 |
| 增量静态再生 ISR | 构建时生成 + 按需/定时再生成 | **本项目访客端采用**；兼顾速度与实时 |
| 服务端渲染 SSR | 每次请求现场拼装 | 内容实时；需服务器常驻 |
| 客户端渲染 CSR | 浏览器内用 JS 渲染 | 首屏慢；适合复杂交互 |

## 附四：对象存储与数据库的分工

- **对象存储**：扁平结构，只有「key → 内容」映射，没有真实目录；界面上的文件夹是模拟的。
- **数据库**：存结构化元数据，支持按条件查询、排序、关联。
- **网页版网盘** = 数据库存目录树 + 对象存储存内容。
- **图书馆比喻**：数据库是目录卡片柜（知道书在哪），存储是书架本身（放着书）。
